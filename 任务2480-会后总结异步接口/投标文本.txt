【详细方案】
Understanding: The buyer needs one runnable endpoint that accepts a meeting transcript and returns a job, then reports progress while a segmented map/reduce pipeline builds a draft. The output must be quarantined in a human review queue at L1, never published, and must never compute amounts. All demo records are fictional.

Pipeline and concurrency: A deterministic mock of transcript preprocessing splits newline-delimited lines into indexed segments. Each segment is mapped exactly once through ops.meeting.map, guarded by a counting semaphore implemented with a FIFO wait queue and a hard limit of four active calls. Each logical call awaits a configurable delay and may retry up to three attempts internally, which makes overlap observable to the concurrency assertion. The map stage updates map_done against map_total so the progress endpoint is meaningful while work is in flight.

Hierarchical reduce: When the segment count exceeds twenty, summaries are split into local groups of ten and each group is reduced with ops.meeting.reduce; the local results are then reduced once more into the final text. Twenty-five segments therefore produce three local calls (ten, ten, five inputs) and one final call (three inputs). Smaller meetings skip reduce entirely and concatenate segment summaries.

Cache, failure and retry: Segment results are stored in an in-memory Redis stand-in with a 24-hour TTL, keyed by SHA-256 of the segment text plus a template version. Every run consults the cache first, so a retry reuses all successful segment results and only calls the gateway for failed ones. A segment that exhausts its gateway retries marks the job failed with error_code MAP_SEGMENT_FAILED and returns the failing segment number. POST /api/ops/jobs/{job_id}/retry is accepted only for failed jobs and re-runs only the failed segments; GET /api/ops/jobs/{job_id} exposes phase, map_done, map_total, failed_segments and error_code.

Review isolation and evidence: The service derives speaker_legend from attendee roles and confidentiality from the meeting type, then passes the envelope through one generic draft-pipeline function that writes a pending_review draft at L1 into review_queue. There is no outbound channel, the outbound counter stays at zero, and amount is always null. An OpenAPI document, a parameter endpoint, call-count metrics, a React 18 + Vite 6 console, Docker packaging and a verification record with real command output are included. Acceptance C1 asserts concurrency at or below four on thirty segments; C2 asserts three local plus one final reduce on twenty-five segments; C3 asserts that retrying a failed seventh segment re-invokes only that segment while the other twenty-nine hit cache; C4 asserts map_done and map_total during the map phase.

Implementation: No special access or real backend is required. Multipart parsing, the semaphore, the TTL cache and the gateway calls are implemented locally with Node built-ins; README marks each production replacement point. Path: scaffold the Express service and endpoints -> add semaphore-bounded map and hierarchical reduce -> add cache, failure codes and retry -> build the demo UI -> add OpenAPI, tests, Docker packaging and the verification record. The runnable repository is at https://github.com/muye1122/meeting-summary-async-2480 .
