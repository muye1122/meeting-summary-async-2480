【详细方案】
Understanding: The buyer wants a self-contained proof that a callback endpoint can verify a signature before doing any decryption, decrypt the payload with the documented enterprise key derivation and packet layout, bind the receiving corporation identity, resist replayed deliveries, and persist each distinct event exactly once. The three credentials must come only from environment variables, and logs must never expose plaintext or keys. A small demo UI plus reproducible vectors and tests make the behaviour inspectable without contacting any real service.

Plan:
1. Implement the crypto module with node:crypto: SHA1 over the sorted token/timestamp/nonce/ciphertext tuple with constant-time comparison, Base64(EncodingAESKey + "=") key derivation, IV from the first 16 key bytes, AES-256-CBC with manual 32-byte PKCS#7 padding, and 16-byte-random + 4-byte-length + message + receiveid packing/unpacking.
2. Implement the callback API: GET verifies the signature and the 300-second timestamp window, decrypts echostr and returns the plaintext; POST verifies the signature and window, decrypts, checks receiveid against the configured corporation identity, parses the inner XML with a small regex reader, and writes a structured event row.
3. Implement replay protection: build a SHA256 dedup key from FromUserName, CreateTime, Event, ChangeType and the related member/external identifiers; enforce a unique key in the in-memory table and in the SQL migration; repeat deliveries return duplicate without touching processed_at or the processed counter.
4. Implement safe logging: a strict field whitelist containing status codes, fixed reason codes, event type and the dedup digest only; no message body, ciphertext, token, encoding key or corporation identity is ever emitted.
5. Build fictional vectors with a self-generated key, deterministic random prefixes, precomputed ciphertext and hand-computed signatures; cross-check them with an independent reference implementation in the tests.
6. Build the React + Vite demo for address verification, repeated event delivery and event-table inspection, with a dedicated security self-check panel.
7. Write README, verification record and Docker packaging, then run install, build and the full test command and record real output.

Data sources: No external datasets or live services are used. Everything is compiled from the requirement page and locally generated fictional placeholders. No real personal information, real corporation identity or real credentials are included.

Acceptance criteria:
- C1 (vectors round-trip and hand-computed signature): three crypto tests compare module output with an independent reference implementation and with the stored fictional vectors, including a UTF-8 body.
- C2 (403 on bad signature and on a timestamp drift beyond 300 seconds): the flow test checks both responses, confirms no decrypt-failure log appears, and confirms no event row is written.
- C3 (three deliveries, one row, one processing): the flow test checks processed/duplicate/duplicate statuses, one stored row, one processed count and unchanged received_at/processed_at.
- C4 (logs contain no plaintext or encoding key): the flow test injects a unique marker into the plaintext, delivers it, then scans the captured log text for the marker, ciphertext, token and encoding key.
