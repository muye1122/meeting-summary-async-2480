# 完整版资源图谱存储方案选型对比

## 0. 本文档范围与证据约定

对三种候选方案做前期选型研究：

- **方案 A**：PostgreSQL 16 关系表（`nodes` / `edges` 两表）+ 递归 CTE，复用现有技术栈。
- **方案 B**：PostgreSQL + Apache AGE 扩展，用 openCypher 查询。
- **方案 C**：单独部署开源图数据库（Neo4j Community 或 NebulaGraph，自托管）。

评估维度共 9 项。每个单元格均给出**官方文档事实 + 引用编号**（`[R编号]` 指向《参考链接清单.md》）。本次为纯文档研究，未安装新软件、未跑基准测试，故所有证据为官方文档事实而非实测性能数值；"能力有无"引用官方功能描述，"优劣判断"为基于事实的工程推断。所有示例数据均为虚构或公开资料，不含客户信息。

## 1. 三方案 × 九维度对比表

| 维度 | 方案 A：PostgreSQL 16 关系表 + 递归 CTE | 方案 B：PostgreSQL + Apache AGE（openCypher） | 方案 C：独立图数据库（Neo4j Community / NebulaGraph 自托管） |
|---|---|---|---|
| **1. 私有部署与升级难度** | 单一 PostgreSQL 实例，可装于客户自有云主机/容器；小版本无需停机式数据迁移，主版本用 `pg_upgrade` 原地升级、免 dump/restore；不引入任何扩展编译。[R1][R14] | 在 A 之上加载 AGE 扩展；AGE 需与 PG 版本匹配（支持 PG 11–18，含 16），需 `make install` 从源码编译；主版本升级时须重装匹配版扩展，比 A 多一步扩展生命周期管理。[R6][R5][R14] | 与业务库并列第二套系统。Neo4j 可自管 standalone 服务，社区版升级常经 dump/load；NebulaGraph 为分布式存算分离架构，升级需多节点滚动操作，难度最高。[R10][R11][R16] |
| **2. 与 pgvector 向量检索结合** | pgvector 本身即 PostgreSQL 扩展，向量列与 `nodes`/`edges` 同库；支持 HNSW/IVFFlat 索引与 L2/内积/余弦距离；图与向量可 `JOIN`，共享 ACID 与 PITR。[R3][R4][R13] | AGE 与 pgvector 同为 PG 扩展，可在同一实例共存；但官方站仅有 pgvector 向量处理社区提案，无原生融合 API，需在应用层把 openCypher 结果与向量查询拼接。[R6][R5][R3] | 图库与向量库分属两套系统，须分别在 PostgreSQL 查向量、在图库查图，再于应用层融合，无法同库 `JOIN`。[R3][R10][R11] |
| **3. 两跳/三跳查询能力** | `WITH RECURSIVE` 支持可变深度遍历，官方提供 `search_graph` 示例含 `depth`、`path` 与 `CYCLE` 防环；两跳/三跳可用固定 JOIN 或 `depth <= 3` 条件表达，足够覆盖一期需求。[R2] | 原生 openCypher 支持可变长路径与模式匹配（如 `-[*1..3]->`），多跳表达比 SQL 简洁；openCypher 为属性图开源查询语言规范。[R6][R8] | Neo4j Cypher 与 NebulaGraph 的 openCypher 兼容语言（nGQL）为图遍历原生设计，任意跳数表达最自然，多跳性能与可读性最强。[R10][R11][R8] |
| **4. 事务与数据一致性（与业务库同步方式）** | 图表与业务表同库同事务，原生 ACID，无跨系统同步、无双写对账；pgvector 同库亦继承 ACID。[R3][R15] | 图数据存于 PostgreSQL 内，SQL 与 Cypher 混合查询处于同一事务上下文；官方称 AGE "supports all the functionalities and features of PostgreSQL"。[R6][R1] | 图库是独立系统，与业务库只能最终一致：可用 PostgreSQL 逻辑复制（publish/subscribe）把变更送至订阅端，但跨库无单一 ACID 事务，需对账与补偿设计。[R15][R10][R11] |
| **5. 备份恢复** | `pg_dump` 生成内部一致的 SQL 转储，可恢复到更新版本；配合 WAL 连续归档做 PITR，可恢复到基础备份后任意时间点。[R12][R13] | 与 A 共用同一套 PostgreSQL 备份体系（pg_dump + PITR），AGE 图数据与扩展对象一并纳入，无单独备份链路。[R6][R12][R13] | Neo4j Community 仅支持**离线** dump/restore，在线备份需 Enterprise 商业许可；NebulaGraph 需对分布式各节点分别备份恢复，恢复流程与一致性校验更复杂。[R16][R11][R9] |
| **6. 运维成本（所需组件与人员）** | 仅 PostgreSQL 一套组件（pgvector 为可选扩展），复用现有 DBA 与监控告警，新增运维负担最小。[R1][R3] | 仍为一套数据库，但需增加 AGE 扩展的版本兼容跟踪与源码编译安装环节，运维复杂度略高于 A。[R6][R14] | 业务库 + 独立图库两套系统；Neo4j 需 JVM 与 standalone 服务运维，NebulaGraph 为分布式多服务、存算分离，需图数据库专门人员，成本最高。[R10][R11] |
| **7. 许可条款（许可名及对商业私有部署的影响）** | **PostgreSQL License**（类 BSD/MIT 宽松许可）：任何目的使用/修改/分发免费、无需书面协议、无 copyleft；商业闭源私有部署与向客户分发无障碍，仅需保留版权与免责声明。[R1] | **Apache License 2.0**（AGE，ASF 项目）：宽松许可含专利授权，保留署名/NOTICE 即可，兼容商业私有部署与再分发；底层 PG 仍为 PostgreSQL License。[R7][R5][R1] | Neo4j Community 为 **GPLv3**（强 copyleft）：纯内部私有使用通常不触发源码公开，但一旦对外分发/随产品交付，衍生作品须按 GPLv3 开源；规避须购 Enterprise 商业许可。[R9][R10] NebulaGraph 为 **Apache 2.0**，宽松，可自由修改、部署乃至作为 SaaS 后端。[R11][R7] |
| **8. 团队技能匹配** | 完全复用现有 PostgreSQL 技术栈，SQL 与 CTE 为已有技能，团队无需新语言，一期交付风险最低。[R2][R1] | 需额外掌握 openCypher 语法与 AGE 扩展管理（图标签、可变长路径等概念），学习曲线高于 A。[R6][R8] | 需掌握 Cypher/nGQL、图建模及独立图库运维（JVM / 分布式集群），技能跨度最大，招聘与培训成本最高。[R10][R11][R8] |
| **9. 数据主权（所有组件须可部署在客户自有云账号，不依赖境外托管服务）** | PostgreSQL 可在客户自有云账号内自托管，数据不出客户账号，无境外托管依赖。[R1] | AGE 作为扩展安装在客户自托管的 PostgreSQL 内，全部计算与存储留在客户账号。[R6][R5] | Neo4j 提供 standalone 自管版、NebulaGraph 源码自部署，二者均可落地客户自有云（满足要求）；但组件数量增多扩大了主权审计面。本方案明确**不采用**境外托管版 Neo4j Aura。[R10][R11] |

## 2. 推荐方案

**推荐方案 A：PostgreSQL 16 关系表（`nodes` / `edges`）+ 递归 CTE，复用现有技术栈。**

理由：

1. **一致性与事务最稳**：图数据、业务数据、向量数据同库同事务，原生 ACID，无需跨系统同步或双写对账，从根源上消除不一致风险。[R3][R15]
2. **与 pgvector 天然融合**：向量与图同库，可 `JOIN`，共享 ACID 与 PITR，无需应用层跨库拼接。[R3][R13]
3. **运维与许可负担最低**：单组件、PostgreSQL License 宽松许可、全栈可自托管于客户云账号，数据主权清晰。[R1][R12][R13]
4. **能力满足一期需求**：两跳/三跳用递归 CTE 即可表达，官方提供 `SEARCH` 排序与 `CYCLE` 防环机制。[R2]
5. **团队技能零迁移**：复用现有 PostgreSQL 与 SQL 能力，交付风险最低。[R2][R1]
6. **演进路径清晰**：若后续多跳复杂度上升，可在**同一 PostgreSQL 实例**上加载 AGE 升级到 openCypher（方案 B），无需迁移底层存储。[R6][R5]

**建议演进**：一期落地 A；二期视真实查询复杂度评估是否叠加 AGE（B）。该路径保护一期投资，且规避一次性引入第二套系统的成本。

## 3. 不选其他方案的理由

### 3.1 不选方案 B（PostgreSQL + Apache AGE）

- openCypher 的多跳表达确实更强，但 AGE 引入**扩展版本与 PG 版本强绑定**及源码编译安装，主版本升级需重装匹配扩展，增加升级摩擦与运维步骤。[R6][R14][R5]
- 需额外学习 openCypher 与图概念，团队技能曲线高于 A；而一期两跳/三跳需求用递归 CTE 已可覆盖，额外复杂度性价比不足。[R8][R2]
- pgvector 与 AGE 的融合仍停留在社区提案级，无原生 API，向量+图需应用层拼接。[R5][R3]
- 结论：不作为一期主方案，保留为二期同库演进选项。

### 3.2 不选方案 C（独立图数据库 Neo4j Community / NebulaGraph）

- **一致性风险**：图库与业务库分离，无法共用单一 ACID 事务，只能最终一致并配套对账/补偿，显著增加正确性设计负担。[R15][R10][R11]
- **运维与人员成本**：引入第二套系统；Neo4j 需 JVM 运维且社区版仅离线备份（在线备份需 Enterprise 商业许可），NebulaGraph 为分布式多服务架构，均需专门技能。[R16][R10][R11]
- **许可风险**：Neo4j Community 的 GPLv3 为强 copyleft，若随商业产品对外交付存在开源义务，需 Enterprise 商业许可方可规避；NebulaGraph 的 Apache 2.0 虽宽松，但无法消除双系统本身的运维与一致性成本。[R9][R10][R11][R7]
- **收益错配**：多跳遍历优势在一期以两跳/三跳为主的需求下无法充分兑现，性价比不足。[R2][R10][R11]

## 4. 结论摘要

| 项目 | 结论 |
|---|---|
| 推荐方案 | 方案 A（PostgreSQL 16 关系表 + 递归 CTE） |
| 演进选项 | 方案 B（同一 PG 实例叠加 AGE），留待二期评估 |
| 一期排除 | 方案 B（复杂度超一期需求）、方案 C（双系统一致性/运维/许可成本） |
| 迁移步骤 | 见《迁移步骤草案.md》，共 7 步（≥5 步要求） |
